# Deutsch by TFRI: project guidance

## Project purpose

An open-source system for learning and retaining German vocabulary, developed by The Faust Research Institute (TFRI). It combines active recall, deterministic spaced repetition and peer-assisted practice, connecting individual study with language use in context.

Vocabulary is represented as lexical units: meaning, grammatical forms and example usage. Individual review supports recall; companion sessions and sentence feedback provide opportunities to apply vocabulary. Core study runs locally, with optional account sync and consent-based community features.

Use **Deutsch by TFRI** as the repository-facing project identity and **Deutsch** as its short name. Describe it as a vocabulary learning system, and reserve “companion” for a connected learner. Personal vocabulary can be organized by lesson or topic and practised alongside course activities. The system complements instruction; it is not a complete language course or an official vhs-Lernportal product. Its goal is durable, usable vocabulary. Community features must support learning and respect consent, privacy and learner wellbeing.

Explain their purpose in plain language. Attribute the project to The Faust Research Institute (TFRI); do not imply that institute authorship establishes scientific validation, optimal intervals or proven learning outcomes.
- Keep the README focused on the learning model, available capabilities, local data, consent and material limitations. Keep setup and operational detail in `CONTRIBUTING.md`, source attribution and license boundaries in `DATA_SOURCES.md`, and detailed implementation constraints in this file. Preserve agreement across these documents without duplicating every engineering rule in the README.
- Distinguish implemented capabilities, experimental previews and proposed work. Treat scheduling and study pauses as heuristics, activity as participation, companion feedback as peer-marked outcomes, and dictionary glosses as context-free. Report content coverage and device verification accurately; never imply universal lookup, pronunciation or phone support.
- Keep interface copy concise and useful for the action or decision at hand. Internal design discussions and implementation details do not automatically belong in the UI. Remove repeated titles, redundant labels and unnecessary explanations. Do not use em dashes in new or revised copy.

## Learning philosophy

- Treat active recall and spaced practice as the core learning loop. Typed production and multiple-choice recognition can supplement recall, but must not be presented as equivalent to mastery. Keep mode outcomes distinguishable; recognition and typed production currently schedule correct answers as Hard and misses as Again.
- Correct scheduled Produce and Choose answers preserve ease. After the first successful review (one day), their Hard interval is max(previous interval + 1, round(previous interval × 1.2)), avoiding one/two-day rounding traps. This is a conservative heuristic, not evidence of mastery. Self-rated Recall Hard retains its original interval and ease rules; misses remain Again. Keep existing history and due dates intact until a new answer is submitted.
- Missing noun forms must distinguish unrecorded data from verified usual-number states. Match curated plural suggestions by exact word/article/meaning, never by spelling alone across senses such as Bank. Preserve recorded learner forms; Use plural is explicit and fills only an empty field without recording study or altering schedules/history. Timestamp plural edits independently so a later review from a stale device cannot erase the lexical correction.
- Teach a useful lexical unit, not an isolated translation. For nouns, preserve and practise article and plural; for every item, prefer accurate, natural example sentences and translations.
- Choose options must be distinct normalized spellings and exclude known overlapping English gloss alternatives and explicit accepted German answers, including study-set fallback. Produce uses the saved lexical target and context; another active saved translation with overlapping meaning is held neutrally until the learner explicitly saves/accepts it or tries the saved target. Do not schedule or score while that decision is pending. Accepted keys are bounded, preserve noun articles, survive imports/backups/sync, and never propagate to another learner through chat.
- Increase challenge gradually and mix practice types where useful. Avoid overwhelming new-card volume, trick questions, ambiguous distractors, and penalties that discourage honest answers.
- Start with Recall when locally saved reviews are due, otherwise Learn when unseen active words exist; retain the completion screen if neither exists. Never switch modes automatically during a visit as progress syncs or reviews become due.
- Learn mode introduces unseen active words in the main card area through guided discovery, browsing, and saved learning; its view and filters are accessed from the top ellipsis menu. Optional checks and session-only skips do not score, schedule, or consume the daily allowance. Adding a word to reviews schedules its first review for ten minutes later and consumes the shared daily new-word target, with explicit confirmation beyond the target; only an actual answer or rating records a review.
- The study area quietly shows when the next first review is due and offers a count without revealing words; it never switches study modes automatically.
- Learn navigation keeps a session-only path through visited words. Previous can revisit skipped words and scheduled or reviewed words; scheduled and reviewed words are read-only. Next retraces the path before continuing. In Continue learning, explain when Next has no other word and offer Guided or Browse; preserve the active filters. Reset the path on view/filter changes or leaving Learn, and never count revisits as study completions.
- App settings provide optional, skippable study pauses: by default, 60 seconds after three distinct words added to reviews or completed in any review mode, including repeat loops. Allowed intervals are 3, 5 or 10 words; pause durations are 30, 60 or 120 seconds. Do not count saves, skips, views, or gentle checks; show quiz feedback before starting a pending pause. Persist settings, count, and deadline locally, use wall-clock deadlines across reloads and background tabs, and never change scores or review scheduling. Settings changes reset the count. Keep the allowed values, tests, and README explanation aligned when tuning this heuristic; do not claim the defaults are optimal.
- Activity calendars count each word once per local day when added to reviews or reviewed, including repeat loops, with overlapping added/reviewed breakdowns. Preserve per-word activity through review resets, backups and account merges; reconstruct available legacy history without claiming it is complete. Do not count views, saves, skips or gentle checks, and do not present participation as mastery or apply streak pressure.
- Give immediate, kind, specific feedback. Explain what was correct and what to revisit; let learners report which detail was difficult.
- Adapt conservatively from repeated evidence. Show why a suggestion was made and keep it optional; do not silently rewrite the curriculum or schedule.
- Let learners set a current level, target level/date, and daily intensity. Use these goals to recommend transparent new-card and review limits, but keep review intervals deterministic and do not imply vocabulary practice alone guarantees CEFR progress.
- Present study-time ranges as broad estimates with a reputable source and clear caveats. Never convert a card quota or streak into a claim of language proficiency.
- Prefer trustworthy, curated content. New installations currently include 2,593 starter cards across core vocabulary and ten themes; source-supplied A1/A2 labels and examples are not independently verified. Keep documented counts and coverage aligned with the source data and tests, and preserve existing decks when updating starter content. Imported or generated material must be validated before it becomes study content; label limitations rather than claiming unverified CEFR accuracy.
- Keep third-party vocabulary data separate from app code and preserve its source attribution, license, and any share-alike requirements when filtering or adapting it.
- Prefer verified, attributed external human pronunciation recordings when available, with a German device-voice fallback and a clear unavailable state. Offer playback in Learn and only after revealing or submitting an answer in review modes. Playback must be initiated by the learner; disclose the external request, show the recording's author, source, license, and modification status, and never bundle or app-cache audio. The source/attribution catalogue matches all current starter headwords, including non-nouns, with some plural forms. Keep coverage tests aligned with the starter set; do not imply every imported word or phrase has a recording. Observe voice-list readiness, prefer local German speech, require a separate explicit choice before remote browser speech, and never substitute another language. Audio metadata is a separate lazy-loaded asset; only a learner click requests external audio.
- The optional offline German voice package is separately GPL-3.0-or-later and not imported into the MIT app; integration uses a same-origin frame with checked message origin, source and nonce. Stable releases require reviewed exact corresponding source, notices, build recipe, cold-start offline behavior and physical iOS/Android checks. The user-approved opt-in preview may be enabled for physical-device testing after source/license/desktop-offline checks pass; label it Preview and keep unverified phone flags false. Downloads must be explicit, bounded and integrity-checked, with cancellation, rollback and removal; never put external human recordings in its cache or send study text to a speech service. Preserve source/model/license provenance in separate release artifacts. Distinguish synthesized attribution from human recordings, keep its service worker isolated, cancel stale playback and release worker resources when hidden or idle. Do not promote the preview to stable or mark phone checks complete without physical-device evidence.
- Let learners organize their own course vocabulary by source, unit, and theme. Do not scrape, reproduce, or claim affiliation with third-party course content; support manual entry and user-prepared imports.
- Respect attention and learner wellbeing: calm interface, short focused sessions, no shame, streak pressure, manipulative rewards, or unsupported claims about learning speed.

## Product and engineering principles

- Evaluate product and UX decisions through engineering, linguistics, and psychology perspectives.
- Keep the card deck as the primary, uncluttered experience. Secondary controls should remain small and purposeful.
- Explain the app's purpose in the first-visit introduction and the About menu without implying it replaces a course or guarantees proficiency. Keep the introduction dismissible and local to the browser.
- Make Learn words and examples, revealed Recall words and examples, and submitted quiz answers available to copy with subtle, accessible icon controls. Keep the text selectable; copying must not reveal or hide an answer, and clipboard failures must be reported.
- Every German example token in Learn and revealed/submitted review answers offers the shared local lookup used by chat. Keep selection/copy intact, preserve distinct senses and personal examples, resolve source-verified inflections back to personal vocabulary, and offer retry after transient resource failures. Exact English counterpart highlights remain limited to verified sentence pairs; never guess alignments or enable lookup that exposes a concealed review answer.
- Keep scrollbars hidden inside cards and let Learn and revealed Recall cards expand for longer content.
- Keep Add a word, Tune session, and Goal & pace in anchored panels; outside clicks must not discard unfinished entries or goal edits. Tune session changes apply immediately.
- App anchored panels use the shared panel layers above the mobile chat workspace, with the active panel in front and portalled selects above it. Chat headers and message actions must never cover an app form.
- Keep scheduling deterministic, testable, local, and independent from AI or network services.
- Minute delays use elapsed timestamp arithmetic across timezone clock changes; day intervals retain local calendar-day arithmetic. Cover both clock-change directions in isolated timezone tests.
- Coordinate every local deck write across tabs, including cloud merges and confirmed replacement. Read latest storage within an exclusive Web Lock or IndexedDB transaction, merge disjoint changes, and reject stale same-word or destructive writes without advancing UI state. Recheck the shared daily allowance inside that boundary; do not automatically switch modes or clear a typed answer when another tab writes.
- Store progress locally by default. Never require a backend for core study; add sync or a database only for a clear user need and with explicit privacy/security design.
- Require email verification for new accounts while allowing existing unverified accounts to sign in and study. Account codes are time-limited, single-use, rate-limited, and stored as keyed digests; password resets invalidate existing sessions. Never expose Mailjet credentials or log codes.
- Require verified accounts for username-only companion connections. Both learners must consent; blocking ends the connection, hides the blocker from the other learner, and prevents requests. Keep email and study progress private, limit requests and notification emails, and honor the recipient's email preference. Companion service failures must not block individual study.
- Companion chat is private 1:1 text between two consenting, verified learners. Current private/group chat and local word lookup do not send messages to an AI or translation service. Do not send chat content to any third-party or AI service automatically; any proposed external processing feature must be an explicit, per-use opt-in that sends the minimum text, runs through the server with rate limits, labels the result as unverified, and never changes a deck on its own. Cap message size and sending rates, let senders edit or unsend briefly, keep report copies for moderation, and never expose email addresses or study progress to companions.
- Review together is an explicit, private companion session: the app randomly selects five previously reviewed active cards, optionally limited to a learner-chosen lesson or topic tag, the helper accepts, and cards are exposed one at a time in a focused review deck that temporarily replaces the conversation. Do not preview the selected cards to either learner before acceptance. Once a helper marks the answer correct or reveals it, show the complete selected lexical unit (meaning, article, plural where present, example, and translation). It supports typed German-to-English meaning recall with kind helper feedback, but never exposes wider deck data, study progress, or schedules. Helper feedback must never create review history, activity, scores, or scheduling changes; either learner can end the session and active card data expires quickly.
- Review together may show a temporary companion waiting or typing indicator in the chat header. Reuse the private chat typing safeguards and respect reduced motion.
- Private chats, group chats and Review together use authenticated Socket.IO WebSockets with the existing HTTP validation and serializers reused in process. Recheck sessions and membership before commands and deliveries, scope each client to its authorized conversation, and never disclose unrevealed review answers. Relay typing without persisting drafts. Use live hints and outage polling as fallback; reconnects reconcile authoritative state and typing expires locally. Direct delivery works on one API instance; multi-instance typing needs a shared transient adapter, while cross-instance saved changes and durable replay require a replica set.
- During Review together, keep the learner's submitted answer visible while awaiting feedback, clearly signal whose action is next, and show failed updates with a way to refresh without discarding an unsent answer.
- Learners can request a reveal before answering or after a retry, including after exhausting attempts. Only the helper can fulfill it. Keep requests idempotent, preserve them across reconnects, prevent competing answers during a pending request, and count the fulfilled reveal once. Word-by-word status animation must retain the complete accessible text, avoid layout shifts and honor reduced motion.
- Ending or completing an accepted review posts only that session's companion-marked outcomes in the private chat, with idempotent summary insertion. Keep first-try recall, recall after retry and revealed answers distinct; never infer overall mastery or disclose wider progress. Cancelled invitations have no results.
- Identify review summaries from their server-generated identity, including existing summaries, with a bright Review tag and a soft accent surface. Ordinary message text must not impersonate a summary. Summaries can be replied to, reacted to or unsent under existing rules, but their generated results cannot be edited or sentence-corrected.
- Healthy socket delivery sends only changed messages; review-only actions skip history. Preserve cached history when merging deltas, resume valid replay cursors, and replace the cached page when replay requires a reset. Avoid identical payloads and redundant storage writes.
- Keep bounded account-scoped chat pages warm across workspace remounts, accept review-summary messages in private cache validation, and hydrate saved history before choosing a full fetch. Only accepted history responses settle initial loading. Show the empty conversation state only after a successful empty response; temporary refresh failures retain history. Replacement flags are one-shot, and authoritative resets must send a complete page even if fingerprints match. Clear warm memory and invalidate stale writers with saved-chat clearing and account changes.
- Groups (`server/groups.js`, `src/GroupsPanel.tsx`) are a separate, opt-in space and must never weaken private chat. Any verified learner can create up to 3 groups and others can join; a creator can edit the name and description, close a group to new members, hide messages and reviews, remove members or delete it. Name changes produce a chat notice. Group text supports reactions, word cards, lookup, search and multiple member reviews; reviews are separately reportable and subject to the hourly message limit. Keep the safeguards: group rules acknowledged before the first create or join, rate limits and duplicate and link limits, reporting with automatic hiding after three reports, a moderator queue (`MODERATOR_USER_IDS`, `src/ModerationQueue.tsx`) that can dismiss, hide or suspend, and retention limits (resolved reports 90 days, messages one year). Show only a username and avatar; never email, study progress, scores, or private chat content. Joining, posting and leaving stay explicit, with no streaks, follower counts, public rankings or infinite feeds. Do not put group content in a deck or send it to an AI service without the same explicit consent rules as chat. Treat any new group capability (links, images, notifications, learner-created rules) as a moderation decision first.
- Peer practice commands must carry the session revision seen by the client. Check it before the action and atomically with its database update, including card index; increment once per accepted mutation. Reject delayed/duplicate commands without changing answers or statistics and keep typed answers available after rejection.
- Corrections and reviews in chat are optional, kind and specific: show only the changed words, offer reason tags and a short note, let the author decide whether to thank or save the sentence, and never change scores or schedules. Do not add shame, pressure or reward mechanics to chat (no streaks, read receipts that nag, or public rankings).
- Group learning should connect shared vocabulary to each learner's own attempt, specific feedback, and later individual practice. Keep any results private, distinguish peer suggestions from verified content, and make deck additions explicit. Describe available capabilities accurately in About and the README; keep technical setup in CONTRIBUTING.md and data attribution in DATA_SOURCES.md.
- Use this word turns a visible shared group word into a linked sentence attempt (maximum 500 characters, compatible with deck sync). Learners can revise their own attempts as follow-ups, receive existing optional peer reviews, and explicitly save a phrase with an English meaning. Validate source group access and shared-word/own-attempt targets on the server. Preserve normal limits, reporting, hiding, unsending and retry idempotency. Do not infer correctness from word matching, mark peer suggestions as verified, or create review history, activity or schedule changes from group practice.
- Group safety keeps external HTTP(S)/www links visible with a concise warning and the existing two-link limit. A narrow normalized whole-word English/German abuse list holds matching new/edited text, shared card fields and suggestion text/notes before delivery, with a neutral placeholder and a human moderation report. Never fetch links or send text to a classifier. Held content stays out of member payloads, quotes, previews, search, mentions and sound hints. Automatic reports do not count toward the three-human-report threshold. Moderators explicitly restore the inspected version or keep it hidden; dismissing a report must not accidentally restore content. Protect unsent/manual-hidden content from stale restores and retain report limits. Document false positives and incomplete coverage; private chats and study schedules stay independent.
- Shared card/chat tap-to-translate checks the learner's deck first, then the bundled starter vocabulary, then the lazily loaded dictionary (`src/data/german-dictionary.json`, built by `npm run data:dictionary`). Keep the dictionary a separate file so it never weighs on the app bundle, keep its source, license and attribution in the file, the lookup card and the README, and present glosses as short and context-free rather than as sentence translations. Only offer **Add to deck** for categories the deck supports, and require an example sentence (the learner writes one when the dictionary has none). Open external lookup links only on a learner's click.
- Preserve saved Learn state through local storage, backups, and optional account sync, independently of review scheduling. A first review must supersede an older saved-learning state even when the save and review occurred on different devices.
- Let learners search reviewed words in the selected study set, inspect recent review details and reset one word or the set. Resetting review progress requires explicit confirmation, affects shared words, and must not let older synced reviews reappear.
- Preserve user data during migrations and imports. Backups must be understandable, validated, and non-destructive by default.
- Keep the offline shell known-good: cache only successful HTML navigation responses, isolate cache errors from successful network responses, and never put API/socket traffic or optional voice downloads into the generic shell cache.
- Maintain accessible keyboard and screen-reader interactions, responsive mobile layouts, reduced-motion support, and offline behavior.
- Commit study actions to durable storage before changing visible progress, feedback, activity, pause counts or navigation. Storage failures leave the current action retryable. Accepted-answer edits carry an independent timestamp, including explicit empty edits; newer stale-device reviews must not erase them.
- Show form validation beside its field and keep floating menus aligned without shifting nearby controls. Use the top-right toast for meaningful action feedback, not Learn saves or individual review or quiz responses; do not report failed storage as a successful save, and keep error notices dismissible.
- Ask for confirmation in the shared dialog (`useConfirm` from `src/confirmContext.ts`) before actions that delete or replace data, cannot easily be undone, or affect another learner or account session. Name the consequence in the dialog, mark destructive confirmations as danger, and default focus to Cancel. Do not confirm reversible, low-impact actions such as reactions, ratings, toggles, saving a word, or sending an ordinary message; a form with its own explicit submit step (such as a report or correction) does not need a second dialog.
- Keep vocabulary fields and learning signals explicit. Do not infer correctness for granular details from a whole-card rating alone.
- Chat conventions: open a conversation at its newest message, let the device Back button close it, keep the conversation list and chat usable in one column on phones, hide scrollbars inside chat surfaces while keeping them scrollable, and respect reduced motion. The floating companion button is shown on the signed-in deck and in Learn, and hidden in the workspace, introduction and pauses. Prefer gray and white surfaces, small pills, pastel accents and few borders; use the app's toast for confirmations and the confirmation dialog for impactful actions.
- Keep chat token highlighting independent of deck size during rendering: build normalized vocabulary indexes only when the deck changes, reuse them for private/group messages and typing updates, and never scan the full deck per displayed word.
- Keep the outbox in the existing account-scoped local chat storage when that preference is enabled: at most 20 messages for 24 hours, one cache record per message. Restore unconfirmed sends as explicit-retry items with the original client ID, never auto-send on reload, and distinguish unconfirmed delivery from a definite rejection. Honor cache clearing, sign-out/account changes and storage failure reporting; confirm before turning off storage if that removes unsent messages.
- Add focused tests for scheduler transitions, imports, and any learning behavior that changes. API behavior (limits, privacy, message edit, unsend, reviews, search) is covered by the account API integration test and its in-memory database stand-in in `tests/fixtures/accountApi.mjs`; extend it with any new route or rule. Run `npm test`, `npm run lint`, and `npm run build` for relevant changes, and restart the API server after changing routes.
- Keep `README.md` and this file in step with the app: update them in the same change as the behavior. Planning notes (`backlogs.md`, `docs/`) are local and ignored by git; never commit or push them.
- Public usage Q&A and product ideas are hosted in Dustymaterial/Deutsch-community Discussions, linked from the README and issue chooser. Implementation issues and PRs remain in saintheraldfaust/Deutsch. Existing main-repository discussions stay available; cross-link useful context without duplicating topics or posting private app content.
